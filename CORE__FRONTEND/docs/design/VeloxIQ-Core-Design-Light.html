VeloxIQ Core design document

The complete visual and interaction design of the VeloxIQ Core web application, written for light mode. Every value below is shown as it renders in light mode. A matching file covers dark mode. Both describe the same components; only the colour tokens, shadows and a few overrides differ.

1. Overview

VeloxIQ Core is the company-level control application of the VeloxIQ platform: it holds the master data (projects, locations, stores, materials, vendors, equipment), people and organisation, policies, approvals and governance. It is a single-page React application used by a tenant admin on a desktop and, in a reduced form, on phones.

2. Design principles

Table first

Most work is reading and editing lists of master records. Tables are the hero: full width, sortable, filterable with chips, searchable, exportable.

Plain words

Labels use everyday language ("4 more needed", "Needed from", "Assign to project") over system terms. A status says what is true or what to do.

One look, two modes

Components never hard-code a colour. Light and dark differ only in token values, so any new screen is correct in both by default.

Safe by default

Destructive actions confirm and ask for a reason; unsaved changes prompt before leaving; privileged actions are hidden from users who lack the privilege.

8. Page patterns

List page

  1. Page head: breadcrumb, title, one-line description, actions (Bulk upload, Add).
  2. Optional filter (for example "Show project").
  3. Row of stat tiles.
  4. Table panel with chips, search, export and row actions.

Detail page

  1. Back link and title with the record code as a sub-line.
  2. Tabs: Details, then related sections.
  3. Key-value grid on a card; Edit opens a dialog or an inline editor.

Form dialog

  1. Two-column grid on desktop, one column on phone.
  2. Required fields first; full-width fields for long text.
  3. Cancel and one primary action; inline errors; unsaved guard.

Dashboard

  1. Stat tiles linking to lists.
  2. Cards with charts and site rows.
  3. Project filter in the card header.

Mode-specific overrides (Light)

  • Primary buttons and the active sidebar item use the navy gradient (#123C94 to #062258).
  • Links use the primary blue (#2A56BE as --sky, #123C94 as --blue).
  • The header and footer chrome are the same white as the cards.
  • Shadows are a faint navy (0.04 to 0.35 alpha); lines do most of the separating.

10. Accessibility

  • Target contrast: text 4.5 : 1 or better in both modes (see the table in section 3).
  • Every interactive element is reachable by keyboard; focus is always visible; a "skip to content" link is the first tab stop.
  • Dialogs trap focus and return it to the trigger; Escape closes them (with the unsaved prompt where needed).
  • Form errors are linked to their field with aria-describedby; required fields are marked with text, not only colour.
  • Status is never colour alone: badges carry a word, charts carry labels.
  • Tables use real table markup; sortable headers announce aria-sort; on phones the cells keep their labels.
  • Touch targets are 44 px (34 px for compact row actions spaced 8 px apart).
  • The page respects prefers-reduced-motion and scales text with the browser setting.

12. Rules and token reference

Do

  • Use tokens (var(--ink)) for every colour, never hex in a component.
  • Keep one primary button per view.
  • Show a word with every colour.
  • Use plain labels and one-sentence descriptions.
  • Confirm destructive actions and ask for a reason.

Don't

  • Don't add a colour without defining it for both modes.
  • Don't use blur, glass or heavy shadows on cards.
  • Don't hide key actions in menus on desktop.
  • Don't show raw codes or ids where a name exists.
  • Don't rely on hover for anything essential.
